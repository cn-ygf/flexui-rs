# flexui-rs 需求分析

> 本文档只做「需求分析」，不写实现代码。分析结果作为后续架构设计与编码的输入。

## 1. 项目目标

用 Rust 从零实现一个**跨桌面平台的 GUI 库**，控件全部**自绘**，不借助任何第三方
渲染引擎或窗口框架，直接调用操作系统原生 API。库名 `flexui-rs` 暗示布局采用
**Flex（弹性盒）**模型。

一句话定位：**「Rust 版的轻量原生自绘 UI 库，一套 API 双平台，未来可 C ABI 导出」**。

## 2. 需求拆解

### 2.1 明确的硬性需求（用户给定）

| 编号 | 需求 | 说明 |
| ---- | ---- | ---- |
| R1 | 跨桌面平台 | 一期只做 **macOS + Windows**，不含 Linux/移动端 |
| R2 | 不依赖第三方渲染库 / 窗口管理器 | 不用 winit / SDL / GLFW / skia / cairo / wgpu 等 |
| R3 | macOS：`NSView.drawRect` 自绘控件，`NSWindow` 管窗口 | 用 AppKit 原生 |
| R4 | Windows：GDI+ 自绘控件，Win32 窗口 API 管窗口 | 用 Win32 + GDI+ |
| R5 | 抽象出统一的 Rust API | 上层写一次，双平台运行 |
| R6 | 预留 C ABI FFI，供其他语言调用 | 未来需求，需在架构上提前留口 |

### 2.2 由硬性需求推导出的隐含需求

R2/R3/R4 一旦成立，就意味着**很多东西必须自己实现**，这些是隐藏的工作量，
必须在需求阶段就点明：

- **绘图抽象层**：把「画矩形/圆角/路径/线/文字/图片/裁剪/变换/透明度」等原语
  统一抽象，分别落到 macOS 的 Core Graphics（Quartz）和 Windows 的 GDI+。
- **文本排版与度量**：文字测量、换行、对齐、字体加载，双平台结果要尽量一致
  （macOS 走 Core Text/CGContext，Windows 走 GDI+）。
- **事件系统**：鼠标（移动/按下/抬起/滚轮/悬停）、键盘、窗口（缩放/关闭/焦点）。
  平台事件 → 统一事件枚举 → 命中测试 → 分发到控件。
- **布局引擎**：Flex 布局 + 盒模型（padding/margin/border）+ 约束求解。
- **控件模型**：控件树、重绘失效（dirty region）、脏区合并、局部重绘。
- **HiDPI / 缩放**：macOS backingScaleFactor、Windows Per-Monitor DPI Awareness。
- **主线程与事件循环**：两平台 UI 都必须在主线程；需要各自的 RunLoop / 消息循环。
- **资源与生命周期**：objc 的 retain/release、GDI+ 句柄与 `GdiplusStartup/Shutdown`。

### 2.3 非功能需求

- **一致性**：同一段上层代码，双平台视觉/行为尽量一致。
- **可分层复用**（AI_RULES 要求）：平台层、绘图层、控件层、布局层清晰解耦，
  上层不感知平台差异。
- **安全边界**：所有 `unsafe` FFI 收敛在平台层，上层 API 保持安全 Rust。
- **FFI 友好**：核心 API 用「不透明句柄 + 函数 + 回调指针」的形态，方便 C 导出，
  跨边界不 panic（`catch_unwind`）。
- **可测试**：核心逻辑（布局、事件路由、几何）可脱离窗口做单元测试。

### 2.4 控件级细节需求（用户补充，2026-08-07）

详细模型见 `06-控件与样式模型.md` 与 `07-布局与XML.md`，此处登记需求条目：

| 编号 | 需求 | 落点 |
| ---- | ---- | ---- |
| C1 | 控件支持 Normal / Hot / Pushed / Disabled 四状态 | 06 状态机 |
| C2 | 每种状态再叠加「有无 focus」= 4×2=8 个样式槽 | 06 状态机 |
| C3 | 每状态可配：背景图/前景图/背景色/前景色/边框色/边框宽/圆角/rect | 06 分状态样式 |
| C4 | 所有控件都是容器，可嵌套 1 个子控件 | 06 单子容器 |
| C5 | Box / VBox / HBox 多子容器 | 06 多子容器 |
| C6 | 可设消息响应「穿透 / 不穿透」 | 06 HitPolicy |
| C7 | 基础控件（Label/Button/Image/Edit/CheckBox…） | 06 基础控件 |
| C8 | 扩展控件如 Radio 支持 group 单选 | 06 扩展控件 |
| C9 | TabBox + Radio 关联 tabbox 实现 tabbar | 06 扩展控件 |
| C10 | 代码布局（类 QWidget）+ XML 布局（类 duilib） | 07 两种布局 |
| C11 | 布局条件语法糖 v-if（类 Vue 条件渲染） | 07 v-if |
| C12 | 按平台条件渲染（如非 macOS 才画系统标题栏按钮） | 07 平台谓词 |

> 决策 D1 已确认：**允许引入 OS API 绑定 crate**（objc2 / windows-rs）。

## 3. 范围边界（一期做 / 不做）

**一期做**：
- 窗口创建/关闭/缩放，主事件循环。
- 基础绘图原语 + 文本绘制/度量 + **图片绘制**（背景/前景图）。
- Flex 布局 + 盒模型；Box / VBox / HBox 容器。
- **控件状态机**（4 基础态 × focus = 8 槽）+ **分状态样式**（色/图/边框/圆角/rect）。
- 基础控件：Label、Button、Image、CheckBox、Edit（可延后）；单子嵌套 + 事件穿透。
- 扩展控件：Radio + group、TabBox、Radio↔TabBox 组成 tabbar。
- 代码布局（Builder）+ XML 布局（`flexui-xml`）+ **v-if 静态条件渲染** + **平台谓词**。
- 鼠标 + 键盘事件、命中测试、焦点。
- HiDPI 适配。
- 统一 Rust API。

**一期不做（明确排除，避免范围蔓延）**：
- Linux、移动端、Web。
- GPU 加速渲染（先纯 CPU/系统 2D API）。
- 复杂 IME 输入法组合、无障碍（Accessibility）、屏幕阅读器。
- 动画系统、主题引擎、富文本。
- **v-if 的响应式重渲染**（数据变自动刷新）——一期只做加载期静态求值。
- 九宫格图片拉伸的完整实现（先普通绘制，拉伸列增强项）。
- 完整的 C ABI 实现（一期只**预留架构**，不铺全量导出）。

## 4. 关键待确认决策（需用户拍板）

以下几点会显著影响架构，建议尽早确认（详见 `04-风险与决策.md`）：

1. **「第三方库」的边界**：`objc2` / `windows-rs`（`winapi`）这类**纯 OS API 绑定
   crate** 是否允许？它们不是渲染库也不是窗口管理器，只是把系统 API 声明成
   Rust extern。**建议：允许**，否则要手写 `objc_msgSend` / 全量 extern 声明，成本巨大、
   收益极低。
2. **macOS 绘图后端**：`NSView.drawRect` 内使用 **Core Graphics（CGContext/Quartz）**
   自绘，作为 GDI+ 的对位。**建议：确认采用**（这是 drawRect 自绘的自然选择）。
3. **渲染模型**：**保留模式**（控件树 + 脏区失效重绘）而非即时模式。**建议：保留模式**。
4. **布局模型**：确认采用 **Flex**（与库名一致）。
5. **异步/线程**：一期是否需要多线程/异步事件？**建议：先单线程主循环**。
